# Native source reference serialization

## Summary

Normalize validated native repository references before generating source files,
so the async broker and canonical JSON host helper reproduce the same approved
owner bootstrap plan. Preserve exact source bytes, authority checks and the
original operation's recovery path.

## Classification

Operator-approved owner-repo maintenance. Landing Unit decision
`feature_single_landing_unit`, `maintenance-native-source-reference-order`.
Extends existing typed source readers; no new workflow, permission or ART item.

## Ownership

OOS owns source proof validation and the broker/host transport boundary.
Platform retains credential custody; Security retains composition acceptance.

## Root Cause

The broker returned an intake reference ordered `id`, `version`, `digest`; the
host helper sorted its JSON keys. Both proofs had the same canonical digest,
but embedding the object using JSON.stringify generated different metadata
file bytes. The exact plan guard correctly refused the source operation.
Earlier tests verified semantic identity without comparing generated bytes
across the actual canonical helper serialization boundary.

## Source Changes

After all existing proof checks pass, project provider and intake/Inventory
references into deterministic typed field order in the shared proof validator.
Use that normalized proof in both readers. Bootstrap, verification and ordinary
source tests exercise original, canonical and reversed transport key order;
bootstrap additionally requires identical complete plans and file contents.

The trusted template is unchanged, allowing an original retained plan to resume
without rewriting its approval, source scope or checkout ownership.
